# Spike decisions

Date: 2026-10-18. Source documents: `docs/spikes/gpui.md`, `docs/spikes/cpal.md`, `docs/spikes/stretch.md` (read those for method, caveats and raw numbers). This record claims nothing they do not support. All spike code is throwaway and lives in `spikes/`. The GPUI and stretch spikes played no audio. Early cpal runs (5 s and 60 s on WSL) were audible: a 440 Hz tone at gain 0.5, before the silent-only rule. Everything since is silent by default; an audible tone is opt-in (`OPENMIXER_AUDIBLE=1`, gain at most 0.05) and user-run only.

**Status (updated 2026-11-07): the engine, analysis, library, MIDI and plugins are verified headlessly on Linux, and the GPUI app runs on Linux. The UI (Wave 5) is partial: staged screenshots were checked by eye, a live window on a real display was not. The platform refresh (sections from "P0 spike" on) is built and tested headless and not yet confirmed on hardware (`docs/testing/hardware-checklist.md`). Windows and macOS support is later. Next: the Before-Wave-7 list in `TODO.md`, then Wave 7.**

The dated sections below are records. Where a later decision replaced one, a line marked Update points to the newer section: the GPUI dependency (now `gpui-pre` 0.3.10 with `gpui-kit` 0.8.1), the MIDI backend (now `midir`), the unsafe policy, CI platforms and deck varispeed.

## Linux first

Decided by the user, with the time-stretch choice made by the author.

- **Scope.** Linux only for now. Windows and macOS support comes later. CI keeps building and testing the Rust workspace on Linux, macOS and Windows so portability does not rot, but no Windows or macOS spike run, device run or listening test is a gate for now. (Update 2026-10-27: CI is Linux only; see "CI status by platform".)
- **GPUI gate: closed on Linux.** `gpui =0.2.2` ran on WSL2 X11 (Spike A). The only remaining Linux check is a native-Linux run on a real GPU: nice-to-have, not blocking. The fallback toolkit (iced, then Slint) stays only for a Linux failure. Windows and macOS GPUI checks come with Windows and macOS support. (Update 2026-11-07: the dependency is now `gpui-pre` 0.3.10 imported as `gpui` with `gpui-kit` 0.8.1 and `gpui-component`, on Rust 1.95; see "P0 spike: gpui-kit with cpal and midir (#218)" and "P5" below.)
- **Real-device audio: Linux (ALSA/PipeWire) only for now.** Windows WASAPI and macOS CoreAudio come later. The headphone-cue second-stream failure on WSLg stays recorded as an open Linux item, to verify on native Linux with a real device.
- **Time-stretch: decided (author call; the user may revisit by ear).** Rubber Band R3 via FFI in a dedicated `om-stretch` crate, the one crate allowed `unsafe` (Update 2026-11-07: the policy is now per-module exceptions with a leak check, see `CONTRIBUTING.md`; `om-stretch` keeps its `unsafe` in `ffi.rs`), behind a small `Stretcher` trait so Signalsmith or a pure-Rust engine can be swapped in later. Rationale: reference quality; GPL-2.0-or-later is AGPLv3-compatible and design-accepted; it was used by the earlier C++ build; stereo CPU is 4.9-5.6% of a core per deck on WSL wall-clock, which is marginal and is to be re-measured in the real engine. The `GPL-2.0-or-later` allow-entry in `deny.toml` is enabled (om-stretch has landed; the reason is recorded in `deny.toml`). The Windows and macOS build cost of the FFI route is a concern for that later work.
- **General rule.** For well-established crates (cpal, symphonia, rusqlite, midir and similar), adopt directly. Reserve spikes for genuine unknowns.

## Spike A: GPUI window (go/no-go gate)

- (Update 2026-11-07: `spikes/gpui-window` now builds `gpui-kit` with `cpal` and `midir`, see the #218 section; the notes below describe the 2026-10-18 run on `gpui` 0.2.2.) GPUI is available on crates.io as `gpui` 0.2.2 (Apache-2.0). It is pinned with `gpui = "=0.2.2"`; no Zed git pin is needed, which supersedes the earlier design note that found no authoritative crates.io status.
- WSL2 X11: runs at 60.0 fps in release (30.0 fps debug, not understood), about 114% CPU. The window was not visually seen (non-interactive session). `vulkaninfo` was not installed. There is no `dzn` ICD and no `/dev/dri`, so the device is most likely llvmpipe (software), unconfirmed.
- WSL2 Wayland (WSLg): panic `UnsupportedVersion` in GPUI's Wayland client; `WAYLAND_DISPLAY=` forces X11. Per the design this is a dev-loop issue and does not fail the gate on its own.
- Build friction: a fresh dependency resolve breaks (`libc` 0.2.191 vs `xattr`); the committed `Cargo.lock` pins `libc` 0.2.188. Needs `libxkbcommon-x11-dev` on Linux. Budget for dependency churn.
- Windows and macOS were not run and are not gates any more (Linux-first, see Rescope). The gate is closed on Linux. A Linux failure would trigger the fallback: a toolkit switch, iced first, then Slint (not dropping the platform).

## Spike B: cpal output callback

- The render path (`render(out, channels, state, cmd_consumer)` driven by an `rtrb` SPSC queue) is allocation-free under `assert_no_alloc`; a mutation check confirmed the guard works.
- Real stream on WSLg through the cpal PulseAudio host: `BufferSize::Fixed(256)` accepted, but the delivered callback size and rate are not confirmed to be exactly 256 frames (mean gap 4% above nominal). No output latency was measured; this is callback-timing jitter only. The ALSA host has no device on this WSL box (build-only). The 60 s run was made before the silent-by-default rule and was audible; a later 4 s silent re-run gave comparable timing.
- Second stream (headphone cue): both attempts failed with "Invalid argument" while the first stream was playing, on the only device available. The cause (cpal Pulse host, WSLg sink, or the probe) was not isolated. Two simultaneous streams are therefore unproven on every backend; this is the main risk carried forward.
- Real-device latency and xrun numbers on native Linux (ALSA/PipeWire) are an open Linux item. Windows (WASAPI) and macOS (CoreAudio) come later.
- rodio correction: the earlier ADR/design wording said rodio cannot control buffer size. That is wrong. rodio 0.23 has `DeviceSinkBuilder::with_buffer_size`. The case for cpal is owning the render callback (allocation-free, SPSC-driven, no iterator-per-sample interface or hidden mixer thread) and opening multiple streams for the headphone cue, not buffer control. Whether rodio can open two devices at once was not checked. rodio remains acceptable for library preview/audition.

## Spike C: time-stretch (keylock)

Design bar: pitch error under 5 cents, and one deck under 5% of a core, judged on stereo. The stereo test material is L plus R = a 0.9x copy of L delayed 331 samples (correlated at 7.5 ms). Measured on synthetic material only, wall-clock on a shared WSL2 VM (plus or minus 20%). Nothing has been heard by an agent.

Stereo CPU per deck: signalsmith 0.8-1.0%; `timestretch` Keylock/batch 2.1-3.1% (but fails pitch at 0.92 and transients); Rubber Band R3 4.9-5.6% (marginal); `timestretch` WideKeylock about 5.0% (4.98% at 0.92, 5.71% at 1.08; transients poor); `wsola` 5.3-6.2% (fails the CPU bar; pitch and transients good).

Findings:
- **No pure-Rust candidate passes the design bar in stereo.** `wsola` and `timestretch-wide` keep pitch but are at or over 5%; the cheap `timestretch` Keylock fails pitch. `wsola` is an unoptimised brute-force search, so tuning might bring it under 5%, but that is untested, and four decks need margin well under 5% each.
- Signalsmith (C++ via `cc`, MIT) passes every measured bar: pitch under 1 cent, attack rise 3.7-7.2 ms (original 2.2 ms), cheapest CPU. It is FFI, not pure Rust. Only its Linux build was tried.
- Rubber Band R3 (`ENGINE_FINER`) is the trustworthy Rubber Band reference: pitch within 3.4 cents on the strict estimator, attack rise 5.4-7.1 ms. R2 (default options) read about 20 cents off on a steady sine; cause not root-caused (a flaw in the vendored build cannot be ruled out), so R2 numbers are not evidence.
- Rubber Band's GPL-2.0-or-later is AGPLv3-compatible, already used in the C++ build, and accepted by the design, so licence is not an argument against it.
- Caveats: synthetic mono material for pitch and transients; no real music, no stereo pitch/transient metrics, no callback worst-case timing, no live tempo-ramp test.

### Options (historical; option B chosen)

- **A. Signalsmith via a thin FFI crate.** Cheapest CPU and passes every measured bar. Costs: not pure Rust, so FFI becomes the default path instead of the fallback; needs a C++ toolchain on every OS (MSVC, Xcode tools); Windows/macOS build cost unmeasured. MIT, so no `deny.toml` change.
- **B. Rubber Band R3 via FFI.** Reference quality. GPL-2.0-or-later is AGPLv3-compatible and design-accepted. Marginal CPU (4.9-5.6% stereo per deck, so four decks would be tight). Same C++ build cost, plus `bindgen`/libclang through `rubberband-sys`. Needs the `GPL-2.0-or-later` entry in `deny.toml`.
- **C. Keep looking for or tune a pure-Rust stretcher.** Keeps the design's pure-Rust-first stance. `wsola` tuning (smaller search range, larger hop, own optimisation) is untested and may or may not get under the bar; whether it sounds good enough is a question for ears.

**Author's recommendation at the time (superseded by the Rescope decision, option B):** after listening, option A if Signalsmith sounds acceptable (it is the only candidate that passed every measured bar with CPU margin), with B as the quality reference to compare against; choose C only if the listening test shows `wsola` is good enough to justify an optimisation effort. This is the spike author's reading of the numbers, made without hearing any output.

## Audio settings and overlay (Todo 29)

Date: 2026-10-18. Covers the audio settings model, the preferences targets and the settings overlay.

- **Model.** `openmixer::audio_settings::OutputSettings` owns the open device and its callback. A change stops the device, takes the callback back, opens the new setup and restarts the callback; a failed change reopens the previous setup and returns the error. Every output of the device is opened (up to 8), so the pair choice is routing. `OutputBackend` has two implementations: `CpalBackend` (the binary) and `MockBackend` (tests and `--mock-device`). Listing devices opens nothing.
- **Routing across devices.** One `OutputPairs` handle lives in the model and every device is opened through it (`CpalAudioDevice::open_with_pairs`), so master and headphone pairs survive a device change.
- **Restore.** The device state is a JSON string (host, device, rate, buffer, channels) in `AudioPrefs::device_state`. Start-up restores it, else opens the default output. `AppTargetsState` keeps what the targets remember across calls (last map, wanted theme, plugin folder, last audio state); the composition owns it, because the targets object lives for the whole app.
- **Tests.** Every new test runs on `MockBackend` (no device opened). The device tests that touch the default cpal output are `#[ignore]`d: run `OPENMIXER_DEVICE_TESTS=1 cargo test -p om-audio --test cpal_device -- --ignored`.
- **Overlay.** `om-ui-gpui::settings_view`. Opened by the Settings button in a header strip above the layout; closed by Close or a click on the scrim. Audio and appearance are live (the theme switches at once in the window). Every page drives its service (see "Settings pages over the services" below). Escape closes the overlay: the card holds focus while it is open.
- **Build notes.** `--mock-device --smoke` exits 0 with that build. The overlay has not been looked at by eye.
- **Not done.** `--settings` start flag; the example-plugin cases of the preferences targets tests wait on Todo 14.

## Settings pages over the services (Todo 29)

Date: 2026-10-19. Crates: `om-ui::settings` (the page models), `om-ui-gpui::settings_view` (the overlay), `openmixer::gui` (the wiring).

- **MIDI.** The page reads the input list from `MidiService` (refreshed when the overlay opens and on each page change, not per frame). Enable and per-input toggles go through the preferences; the applier opens inputs. Map file: a typed path is loaded first and stored only when it loads; the Load button reloads the map in use. Learn targets are full router ids (`deck.<i>.play|rate`, `mixer.ch<i>.fader|trim`, `mixer.crossfader`, `mixer.master`). A learn that finishes shows as a change of the map generation.

- **Plugins.** The built-in catalog is `openmixer::plugins::builtin_catalog()` (the gain example, linked in as a dependency). Built-ins are not loaded at start-up. Loading or unloading a plugin re-syncs its themes into the window's registry (`sync_plugin_themes`), so they appear in Appearance.

## MIDI device layer (Todo 32)

Date: 2026-10-19. Crate: `crates/om-midi` (`backend.rs`, `midir_backend.rs`, `mock.rs`).

- **midir on every platform (#220).** `MidirBackend` (`midir_backend.rs`) replaces the direct ALSA backend and the non-Linux stub. midir 0.11 resolves now that the workspace is on `gpui-pre` (see the #218 spike below): ALSA sequencer on Linux, CoreMIDI on macOS, WinMM on Windows, one `alsa` in the tree (shared with cpal). The crate no longer depends on `alsa` directly and has no unsafe code. Each routed direction is its own midir client named `openmixer`; inputs ignore sysex, timing and active sensing, as the old backend forwarded channel messages only.
- **Port ids.** midir's Linux names end in the sequencer address (`Client:Port 24:0`), which changes on replug. The id (and the displayed name) is the name without that address, `Client:Port`, so saved preferences survive a replug. Ports of `Midi Through` and of the app's own `openmixer` clients are not listed. Saved ids from the old backend (the bare port name) no longer match and are re-chosen once; two identical devices share an id and the first wins.
- **Tests never open hardware.** `MockBackend` delivers injected bytes and records sent bytes. Every routing, selection, hot-plug and feedback test runs on it.
- **Trait boundary.** `MidiBackend` is the only thing the device-facing code knows. Input callbacks run on the backend's thread and take only the mapper's locks; feedback is evaluated on a control thread at 30 Hz, and hot-plug is checked about once a second.


## Plugins: in-process only (Todo 10a)

Date: 2026-10-19. Crate: `crates/om-plugins`. Example: `examples/plugins/gain-plugin`.

- **Decision: plugins are in-process for now.** A plugin is a Rust type that implements `Plugin`, registered with `PluginRegistry::add_plugin` (built-ins, tests, or a crate the application links). The registry enforces these rules: unique ids, refused duplicate stage, map, prefix and theme names, and unload that removes everything a plugin registered before its `on_unload`.
- **Dynamic loading: superseded on 2026-10-26.** This bullet deferred the choice between a C ABI, a WASM component and source-only plugins. The C ABI was chosen; see "Plugins: C ABI dynamic loading (Todo 10a)" below. No allow-list or signature check is planned (CONTRIBUTING, "Extensibility").
- **Design note.** `Plugin::info` and `Plugin::api_version` take `&self`. Associated functions with no receiver would make the trait unusable as `Box<dyn Plugin>`, which the registry needs.
- **Stage insertion goes through `InsertPoint`.** `MixerControl` and `DjEngine` implement it, so the catalog can be tested over a stub and a plugin stage can always be cleared by the handle it was inserted through.

## Plugins: C ABI dynamic loading (Todo 10a)

Date: 2026-10-26. Crate: `crates/om-plugins` (`abi.rs`, `loader.rs`). Example: `examples/plugins/gain-plugin-cdylib`. Supersedes the "Dynamic loading is a later decision" bullet above.

- **Decision: a C ABI, loaded with `libloading`.** A plugin library exports one `extern "C"` symbol, `openmixer_plugin_entry`, that returns `*const PluginVTable`. The table is `#[repr(C)]`: `abi_version: u32`, then `info`, `create`, `destroy` and `process` as `extern "C"` function pointers. Any language that can export C functions can write a plugin, and the host and plugin need not share a compiler or crate versions. WASM was rejected: it adds a runtime dependency and a host-call cost on the audio path. Source-only plugins would leave the gap open.
- **Version field.** `PLUGIN_ABI_VERSION` (now 1) is the first field. The host reads it before any other field. A value the host does not speak is refused with `PluginError::BadAbi { found, expected }`, and no function in the table is called (the host speaks 1 and 2 since ABI 2, below; this section describes version 1). Any change to the table's layout or meaning bumps the version.
- **Entry checks.** A missing symbol is `PluginError::MissingEntry`. A null table, a null function pointer, or a file that is not a loadable library is `PluginError::InvalidLibrary` with the reason.
- **`info(buf, len)`.** The plugin writes a NUL-terminated UTF-8 JSON object of at most `len` bytes, NUL included, into the host's buffer: `{"id": ..., "name": ..., "version": ..., "stage_id": ..., "kind": "fx" | "pre" | "post"}`. `stage_id` defaults to the id and `kind` to `fx`. The host owns the buffer. Text without a NUL, text that is not UTF-8, or JSON without the three required strings is refused.
- **Mapping onto `Plugin`.** The loader returns a `Box<dyn Plugin>` adapter, so the registry treats a library like any other plugin: unique ids, and unload removes what it registered. In `on_load` the adapter registers one stage factory. Each stage the factory makes holds two plugin instances, one per channel. `process(instance, samples, frames)` handles one mono buffer: the stage calls it for the left slice, then the right. A stateful plugin (a filter, say) keeps per-channel state that way, and the audio path needs no scratch buffer. `ProcessStage::process` has no return value, so `process` has none either.
- **`create` is probed at load.** The loader calls `create` and `destroy` once, so a broken plugin fails at load with an error and not later on the audio path. `StageFactory` cannot fail. If `create` returns null when a stage is attached later, that channel passes audio through unchanged.
- **Ownership rules.** The host owns every audio buffer and the info buffer. The plugin must not keep a pointer to either after the call returns. The plugin owns each instance from `create` until the host passes it to `destroy`, exactly once. An instance is used by one thread at a time but may move between threads (control thread to audio thread). The library is never unloaded while an instance lives: the adapter and every stage hold a shared handle to the library, and a stage destroys its instances before releasing that handle. The library unloads when the plugin is unloaded and the engine has dropped the plugin's last stage.
- **Threads and real time.** `process` runs on the real-time audio thread: it must not allocate, lock, block or do I/O, and must take bounded time. `create`, `destroy` and `info` run on the control thread, possibly while other instances of the same plugin are processing, so a plugin's global state needs its own synchronisation. A plugin that needs memory or setup for `process` does it in `create`, or in `prepare` (ABI 2, below).
- **Panics and unwinding.** No plugin function may unwind. A plugin catches its own panics at the boundary: `create` returns null, and `process` leaves the buffer as it is. Rust aborts the process if a panic reaches an `extern "C"` boundary, and a panic cannot cross into the host anyway (each library has its own copy of std, so the host's `catch_unwind` would see a foreign exception). The host still wraps every call into the plugin in `catch_unwind`, so a panic on the host side of the call (in the adapter) becomes an error or a passthrough and does not escape. A null `create` at load is an error, and the host carries on.
- **`unsafe` is confined.** `om-plugins` denies `unsafe_code` crate-wide and allows it only in `abi.rs` and `loader.rs`. Every block has a `// SAFETY:` comment. The example cdylib needs `unsafe` on its side of the boundary (`#[no_mangle]`, raw pointers), so it denies `unsafe_code` and allows it only on its exported functions. Loading is open by default, with no allow-list or signature check (CONTRIBUTING, "Extensibility"). Loading a library runs its initialisers, so a plugin folder must be trusted like any other program.
- **Tests.** `crates/om-plugins/tests/dynamic_load.rs` builds the example cdylibs with `cargo build` into the test temp dir. They have no dependencies, so each feature variant builds in seconds. Covered: the example loads and halves the gain, a wrong ABI version, a missing entry symbol, a panic in `create`, and a non-library file named `.so`. ABI 2 tests are listed below.

### ABI 2: prepare, parameters, status returns (Todo 10a follow-up)

Date: 2026-10-27. Files: `abi.rs`, `loader.rs`, `api.rs`, `registry.rs`, `crates/om-plugins/include/openmixer_plugin.h`, `examples/plugins/param-plugin-cdylib`.

- **Version negotiation: accept 1 and 2, refuse the rest.** `PLUGIN_ABI_VERSION` is now 2 and `PLUGIN_ABI_MIN` is 1. The host reads `abi_version` first and then reads the table with that version's layout. A version 1 plugin (the gain example, unchanged) loads and runs as before: its stage passes `prepare` by and it has no parameters. Any other value (0, 3, ...) is `PluginError::BadAbi` and nothing in the table is called. The version 2 layout extends version 1 in place (same first five fields), so the version field alone selects it. A plugin can ship a version 1 table to reach hosts that predate this change. We accept 1 deliberately: it costs one read path and keeps the existing example plugin and any plugin built against the first header working. When version 3 appears the rule stays "newest and one back is a decision per version"; nothing is promised for older tables.
- **What changed in the table.** `process` returns an `i32` status (`0` ok, `1` rejected, `2` fault); a non-zero status makes the host stop calling that instance and pass audio through. New optional pointers, null when unsupported: `prepare(instance, sample_rate, max_block) -> status`, and the group `param_count() -> u32`, `param_info(index, buf, len)`, `param_get(instance, index) -> f64`, `param_set(instance, index, value) -> status`. The parameter functions are all present or all null (a half-filled group is `InvalidLibrary`).
- **`prepare`.** `LibraryStage::prepare` (the `ProcessStage` method the engine already calls on the control thread) forwards `sample_rate` and `max_block` to both instances. A plugin must still process before it is prepared. A `prepare` that panics or reports a fault faults the instance (passthrough).
- **Parameters.** At load the host calls `param_count` and `param_info` once per index; each info is JSON `{"id","name","min","max","default"}` (ids unique and non-empty, `min <= default <= max`, at most 256). The initial value is the plugin's `param_get` on the probe instance when it is in range, else the default. They surface through the in-process trait as `Plugin::parameters()` and `Plugin::parameter(id)` (default: none), and `PluginRegistry::plugin_parameters` and `plugin_parameter`. Setting goes through the registry's existing parameter-target path: `on_load` registers a `ParameterTarget` under the prefix `param_prefix` from `info` (default: the stage id), so the router accepts `"<prefix>.<id>"`. The target clamps to `[min, max]`, refuses unknown ids and non-finite values, stores the value in a host atomic and bumps a generation counter. Each stage compares the counter at the start of `process` and, when it moved, calls `param_set` on its instances. That is an atomic load per buffer and no allocation, lock or channel. `param_get` is used for the initial value only; `Plugin::parameter` reports the host's stored value.
- **Panics.** Unchanged in rule, stricter in effect: a plugin catches its own panics (the example's `guard` helper wraps every export in `catch_unwind`) and returns `STATUS_FAULT` (or null from `create`), and the host wraps every call in `catch_unwind` too. A fault in `process`, `prepare` or `param_set` stops that instance for good; the stage passes that channel through. The buffer's content after a faulted call is unspecified; the plugin should leave it untouched.
- **Header.** `crates/om-plugins/include/openmixer_plugin.h` states both layouts for C and C++ plugins. It was syntax-checked with gcc and g++; no plugin has been written in C or C++ against it yet.
- **Tests.** `param-plugin-cdylib` has no dependency on the host crates; it mirrors the header, as an out-of-tree plugin would. `dynamic_load.rs` covers: a version 1 plugin still loads; parameter enumerate, set through the `ParameterRouter` (clamping, unknown id, NaN), a new stage starting from the current values; `prepare` (a 1 kHz tone at 48 kHz and at 96 kHz); a `process` that panics inside the plugin, is reported as a fault and is contained (the stage passes through, the host carries on, a new stage is healthy); the audio path under `assert_no_alloc` including a parameter push; unload removing the target. Version 3 is refused (the `bad-abi` variant reports 3).
- **Not covered.** A plugin that lets a panic cross `extern "C"` (Rust aborts the whole process, so it cannot be tested in-process); a plugin that is not Rust; Windows and macOS libraries; a plugin whose `param_set` is slow.

## P3: rubato for offline resampling; deck varispeed stays linear (#221)

Date: 2026-11-06. Update 2026-11-07: deck varispeed was switched to rubato in #241 (default sinc 128, linear fallback); see "Deck varispeed through rubato" below. rubato 5.0.1 (`audioadapter-buffers` for its buffers); `om-stretch` stays for key lock.

- **Done.** `om-stems` `StreamResampler` and the sampler's `Sample::load` resample now use rubato's synchronous `Fft` resampler (a fixed ratio is its case). Both are offline, so this removes two hand-written sinc kernels and keeps behaviour: exact output length, any chunking gives identical output. `om_engine::resample::fft_resampler` builds it. rubato reports its delay as `fft_size_out / 2` rounded down, so an odd output block leaves a half-frame error after trimming (96 kHz to 44.1 kHz gave a 7% sine error); the helper picks an even block. Rates are whole Hz (container and model rates are); a fractional rate is rounded.
- **`set_resample_ratio` does not allocate** (read in rubato's `asynchro.rs`: it checks bounds, stores the ratio and recomputes two lengths; the out-of-bounds error carries plain numbers). Proven under `assert_no_alloc` in `om-engine` (`rubato_eval.rs`), with ramped and unramped changes and a rejected ratio, for both sinc and polynomial `Async`. `process_into_buffer` allocates nothing either. `StreamResampler::push` and `finish` are proven in `om-stems/tests/resample_alloc.rs`.
- **Deck varispeed: better and affordable, not switched in this change.** Measured with `cargo test -p om-engine rubato_against -- --ignored --nocapture` (256-frame stereo block, ratio moved every block): `Async` sinc 128 taps 27 us (0.5% of the 5.8 ms budget), sinc 256 taps 44 us (0.8%), cubic polynomial 3.5 us. A 10 kHz tone at a 1.08 step: linear interpolation leaves a -22 dB residual and loses 16% of the gain; sinc 256 leaves -107 dB at unity gain. What stops a drop-in swap: the sinc filters add a delay (59 and 118 frames) that the position, loop, slip and sync paths would have to absorb; the ratio cannot be zero or negative (pause, scratch, reverse), and it is bounded by `max_resample_ratio_relative`; a seek or loop wrap must reset the filter history; and `position_frames` is read from the interpolator's frame index. Polynomial (delay 1) is cheap but has no anti-alias filter. Proposed follow-up: an `Async` varispeed behind the same `Playback` interface for the forward, non-zero rate case only, keeping the linear path for scratch and reverse, with the delay folded into the position.

## Deck varispeed through rubato: constraint check (#241)

Date: 2026-11-07. Plan: the #221 follow-up (varispeed through rubato's `Async` resampler in `crates/om-engine/src/deck/playback.rs`). This is step 1, the check of the four constraints from the #221 report against the code, done before any change.

- **Who sets `rate`.** `Deck::set_rate` is the only writer (`deck.rs`); it clamps to `0.0..=MAX_RATE` (8.0). Callers: the `DeckParam::Rate` parameter (UI pitch widget, MIDI, automix) and `Sync::step` (follower rates). So the rate is never negative: **no reverse exists in the engine**, and the request in the plan to bypass the rubato path for reverse is already met by the clamp. There is **no scratch** either: `slip.rs` and `deck_control.rs` talk about a ghost playhead for loops, holds and (future) scratch, but nothing writes a scratch rate. Rate 0 is reachable (a playing deck at rate 0 holds one frame).
- **What already bypasses `render_interpolated`.** Only key-lock (`render_keylocked`, `om-stretch`), and its priming phase calls `render_interpolated` itself. Pause does not reach any renderer (`render` returns silence while `playing` is false).
- **Constraint 1 (filter delay): holds.** `Async` sinc with `sinc_len` 128 delays by 64 source frames (`sinc_len / 2`; the earlier 59 and 118 were output-side figures), cubic polynomial by 2. Checked against a ramp, which a band-limited interpolator reproduces exactly: the published position is within 1.5 source frames of the audible frame over 10 s at steps 1.08 and 0.9. Reported position, loop wrap and sync must be compensated. Slip and sync read `Deck::position_frames()` on the control thread (`deck_control.rs`, `sync.rs`), and nothing else reads the interpolator index, so compensating the one published atomic is enough for both; no om-core trait changes.
- **Constraint 2 (ratio must be positive, bounded): holds.** `set_resample_ratio` rejects values outside `1/max..max` of the constructed ratio and zero. The rubato path therefore takes only effective steps (source frames per output frame, `rate * file_rate / device_rate`) in 0.25..=2.0: the resampler is built at unity with a relative range of 4, the cap of 2 is because the filter is built for unity and a larger step aliases the top of the band, and 0.25 leaves room for a 44.1 kHz file on a 96 kHz device. Rate 0, extreme rates and key-lock stay on the linear path. Exactly unity (`|step - 1| < 1e-6`) also stays linear: linear interpolation at unity is bit-exact and delay-free, which is better than any filter.
- **Constraint 3 (reset on seek and loop wrap): seek yes, loop wrap no.** Seek and handshake go through `reset_playhead`, which marks the rubato state cold (a fresh start, filter zeroed). A loop wrap is different: the wrap point is in the input stream, and the filter holds the last 64 frames of the loop end, which are the frames that should precede the loop start when the loop is seamless. Resetting there would drop 64 frames of the loop and add a gap, so the filter is **not** reset at a wrap; the published position is mapped through a per-frame index history instead of `input - delay`, so it stays right across the wrap. A loop whose slot is not ready falls back to a ring reposition (not gapless), which starves the input and refills it like any other underrun.
- **Constraint 4 (`position_frames` from the interpolator index): holds.** The published value is now the source index of the last frame played, looked up in a 512-frame history of fed frames (so loop wraps map correctly), not the index the input side has reached.
- **Not changed:** no public `om-core` trait is touched; the swap lives wholly behind `Playback`.

### Result (#241)

- **Built.** `VarispeedQuality { Linear, Polynomial, Sinc }` (default `Sinc`, 128 taps), an engine-level setting only: `DjEngineAudio::set_varispeed_quality` / `DeckAudio::set_varispeed_quality`, applied before audio runs. No UI setting (the user's call). Falls back to linear for rate 0, steps outside 0.25..=2.0, exact unity, and key-lock (untouched). A mid-play switch between the two paths blends over 64 frames from the old path's last frame; going back to linear replays the frames the filter held, so the position carries over.
- **Seek and start.** A cold start skips the filter's ring-in from silence, so audio begins at the target. The onset still rings for a few dozen frames, as any band-limited filter does at an abrupt edge; `rate_half_advances_half_as_fast_and_interpolates` now reads its slope past the start.
- **End of track.** The last ~130 source frames (filter delay plus one chunk, about 3 ms) are not played: the input runs dry before the filter has flushed. Not fixed here.
- **Measured** (`cargo bench -p om-engine --bench varispeed`, one 256-frame stereo deck block at rate 1.08 through the full render path, release, host load average about 10 on 12 cores, other agents building): see the PR for the table. Sinc 128 is 0.2% of the block budget at 44.1 kHz and 0.4% at 96 kHz, far below the 2% line, so sinc stays the default.
- **Residual** (1 kHz tone, least-squares sine fit): below -80 dB at steps 0.9, 1.0 (forced through the filter) and 1.08; linear stays above -80 dB at 1.08.

## P9: real-time priority for the audio callback only (#228)

Date: 2026-11-06. cpal 0.18.2 with `audio_thread_priority` 0.35 (cpal's own dependency; om-engine does not depend on it).

- **Callback thread only.** cpal promotes the thread that runs the audio callback and reports a refusal on the stream's error callback, which `om-audio` logs and counts; the stream keeps playing at normal priority (fail soft). The callback code is not touched.
- **Deck decoder workers are not promoted.** They read and decode files, which blocks and can burn CPU for long stretches. On Linux the promotion sets `RLIMIT_RTTIME` to the burst budget, and passing it raises `SIGXCPU`, which ends the process. A decoder has no safe budget, so it stays at normal priority.
- **Linux needs D-Bus.** `audio_thread_priority` is a no-op on Linux without its D-Bus (rtkit) path. That path builds `libdbus`, so it is the `om-audio` feature `realtime-dbus`, off by default, and `libdbus-1-dev` is not a build requirement. Linux builds therefore run the callback at normal priority unless they enable the feature. Windows enables cpal's plain `realtime` feature (no system library). Whether `openmixer` should forward `realtime-dbus` was open: it is a packaging choice, and the GPUI tree avoids system libdbus by using `zbus`.
- **Update (2026-11-07).** The owner decided to forward it: `openmixer` has a `realtime-dbus` feature (`om-audio/realtime-dbus`) that is in `default`, so Linux builds now need `libdbus-1-dev` (CI installs it) and run the callback at real-time priority when rtkit grants it. `--no-default-features` builds without libdbus. The statements above about "off by default" describe `om-audio` alone.

## Faceplate P2: fonts and type in GPUI

Date: 2026-11-08. `gpui-pre` 0.3.10 on Linux (the cosmic-text system of `gpui-pre-wgpu`, over `fontdb`). - **Weights from static files work within one family.** `fontdb` names a face by its typographic family (name ID 16, else ID 1) and GPUI picks the nearest `usWeightClass` among the faces of the requested family. Source Sans 3 Regular (400) and Medium (500) both register as "Source Sans 3"; 400 and 500 resolve to different faces (Medium is wider), 600 and 700 to Medium. The plan's fallback, one family name per weight, is not needed, and would not work with these files: "Source Sans 3 Medium" resolves to a system fallback face.
- **Ubuntu Mono has no 500.** The family ships Regular and Bold only, and the comps load `Ubuntu+Mono:wght@400;700`, so a browser draws DESIGN.md's 500 numerals in Regular. Bundled: Regular; a 500 request resolves to it. Bold is not bundled (the mono 700 deck-tag letter of Phase 3 would need it). Sansation: Bold only, the one weight DESIGN.md uses.
- **Letter-spacing is not available.** `TextStyle`, `TextRun` and `Font` have no tracking field and the shaper takes none. DESIGN.md's -0.01em on the 34 px display tier (about -0.3 px a glyph) and the label caps tracking are dropped; drawing them would take a per-glyph element. Not done.
- **Tabular figures.** Source Sans 3's default figures are already tabular ("1111" and "8888" lay out the same width with and without `tnum`); `font.tabularNumerals` still asks the body family for `tnum`. Numbers are set in Ubuntu Mono anyway (`font::numeral`).
- **Fallback.** An unknown family resolves to a system face. The rating stars (U+2605, U+2606; Inter had them) are not in Source Sans 3 and come from a system font (DejaVu Sans here); a system with none shows boxes.
- **The component library.** `theme_bridge` names the body family as `Theme::font_family` (so its `.SystemUIFont` probe is skipped) and the mono family as `mono_font_family`. Its text is sized in rems of `Theme::font_size` (buttons, inputs and tabs 0.875 rem, extra-small buttons 0.75 rem), so the rem is set to body / 0.875 (14.9 px): small text 13 px, extra-small 11.1 px. With the rem at body size it would be 11.4 and 9.75 px (with Inter's 14 px it was 12.25 and 10.5). The window root sets 13 px so unsized text stays on the body tier. Component button labels keep weight 400 (Medium needs the control rebuild, Phase 3).
- **Fit, measured.** "OPENMIXER" in Sansation Bold 21 px is 124 px wide and the header brand rect is 112 px, so the wordmark stays in the body family until the header is laid out again (Phase 5). The latency counter in mono 13 px reaches 124 px ("123 ms  12 dropouts") in a 120 px rect.
- **Licences, read in full.** Files from the official repositories; each file's Git blob hash matches the repository listing.

  - Source Sans 3 Regular and Medium 3.052 (`adobe-fonts/source-sans`, `release` branch, `TTF/`): SIL OFL 1.1, copyright Adobe, Reserved Font Name "Source".
  - Ubuntu Mono Regular 0.80 (`google/fonts`, `ufl/ubuntumono`): Ubuntu Font Licence 1.0, copyright 2011 Canonical Ltd. It is OFL 1.1 without the "not sold by itself" clause and the reserved names, with a stricter rename rule for modified versions and no trademark grant.

## Faceplate P3: depth, focus and states in GPUI

Date: 2026-11-08. `gpui-pre` 0.3.10 (wgpu renderer, `shaders.wgsl`) and `gpui-component` 0.8.1. Code: `crates/om-ui-gpui/src/paint.rs`, `parts.rs`, `controls.rs`, `gallery.rs`; `crates/om-ui/src/style/face.rs`. Method: the sources of the paint path, then the controls gallery rendered offscreen with gpui's own headless wgpu renderer on Mesa lavapipe (software Vulkan; no display, no GPU) and the PNGs looked at.

- **Inset shadows exist.** `BoxShadow { inset: true }` is drawn as the complement of a (blurred) hole rect clipped to the element's rounded bounds; with blur 0 the edge is a crisp 1 px with antialiasing. So DESIGN.md's `inset 0 0 0 1px` and `inset 0 1px 0` are both expressible; no second quad is needed.
- **Paint order decides the recipe.** `Style::paint` draws drop shadows, the background, inset shadows, the children, then the border on top. CSS draws an inset shadow inside the border. The etched line is therefore a 1 px border (which the disabled state needs anyway: `BorderStyle::Dashed`, dash twice the width, gap once), and the top highlight is an inset shadow offset 1 px down with a spread equal to the edge width, which leaves exactly the 1 px row under the border, as the canvas "States" buttons draw it (`border: 1px` plus `inset 0 1px 0`). The press is `inset 0 1px 2px` pulled in the same way. DESIGN.md's own pairing (`inset 0 0 0 1px` with `inset 0 1px 0`) would hide the highlight under the line in a browser too; the canvas form is the one used.
- **The small drop** is a plain `BoxShadow` (`0 2px 3px`, `0 3px 5px` at the theme's shadow colour); the shader samples a Gaussian. Painted controls use `Window::paint_drop_shadows` then `paint_quad` (knob caps). Only knob and fader caps carry it, as in the canvas; buttons and pads do not.
- **Focus ring: no outline in GPUI.** There is no outline or outline-offset, and a drop shadow with a spread fills the 2 px gap. The ring is a canvas over the control that paints a transparent quad with a 2 px border, dilated 4 px, its corners the control's radius plus 4. It shows while the control's `FocusHandle` is focused and `Window::last_input_was_keyboard()` (the test gpui's own `focus_visible` uses), so a click never shows it. Handles are kept per element id so the ring can ask; a clipping ancestor cuts the ring, as `overflow: hidden` does to a CSS outline.
- **Own buttons, not the component `Button`.** The component's pressed style is set inside its render and replaces any caller refinement, so it cannot sink into the well with an inset shadow, dash a disabled edge or draw the offset ring. Faceplate buttons are stateful divs: `hover` and `active` refinements of the same face recipe, `on_click` (gpui fires it for Enter and Space on a focused element), a prevented mouse-down so a click does not take keyboard focus, role and label for accessibility. The component widgets (settings, library toolbar, dialogs) are themed to the nearest match: rest, hover and pressed fills, secondary text at rest, and the component's own focus ring outside the edge (3 px at half strength, no offset). It cannot dash a disabled edge.
- **Deck tint.** The canvas mixes `color-mix(in oklch, hue 22%, control)`. The app mixes in OkLab (`style::tint`), which keeps the deck's hue; oklch would turn the near-neutral face's hue partway, a small shift at these chromas.
- **Offscreen rendering works.** `gpui::HeadlessAppContext::with_platform(text_system, assets, gpui_platform::current_headless_renderer)` renders a window to an `RgbaImage` through `WgpuHeadlessRenderer` (2x scale), and lavapipe runs it (`VK_ICD_FILENAMES=.../lvp_icd.json`). The renderer factory needs `gpui-pre-platform`'s `test-support` feature, which the workspace cannot enable through `gpui-kit` (its `test-support` pulls `gpui-fast`, whose `taffy` pin conflicts) and which would be a new direct dependency otherwise; the captures were made from a scratch crate outside the workspace, not committed. The headless gallery test in the workspace uses gpui's test platform (layout and painting, no rasterising).
- **Not verified:** on a real display or GPU (only lavapipe rasters were looked at), hinting of the 10 px scale and the 11 px state words, and the component widgets' states by eye.
