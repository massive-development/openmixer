# Crate responsibilities

Dependencies point toward `om-core` (see "Crates" in `AGENTS.md`). The directory tree is in [project-structure.md](project-structure.md) and the README's Architecture section; this is what each crate owns.

- **`om-core`** (no I/O): `ParamId` (control ids, parsed once, canonical `Display`), `Command` and `CommandSink`, `ParameterRouter` (typed dispatch plus the string façade), `StateId` and `EngineSnapshot` (pulled engine state), `WorkerPool` (job queue), `LockExt`, and the `ParamTarget` trait. Typed error enums: `ParamError`, `CommandError`.
- **`om-engine`** (audio thread): decks, mixer, FX racks, sync, loops, sampler, recorder and the EBU R128 loudness meter. Decks resample through `rubato` (`deck/playback/varispeed.rs`, sinc 128 by default, linear for rate 0, steps outside 0.25..=2.0, exact unity and key-lock). Implements `ParamTarget` for each typed target; `DjEngine::snapshot()` builds the snapshot on the control thread.
- **`om-audio`, `om-dsp`, `om-stretch`**: device layer (cpal; the `realtime-dbus` feature, on by default in `openmixer`, asks rtkit for real-time priority on Linux and needs `libdbus-1-dev`), DSP, and key-lock time-stretch (FFI `unsafe` in `om-stretch/src/ffi.rs`).
- **`om-analysis`, `om-library`, `om-midi`, `om-stems`, `om-plugins`**: control-side services with their own typed errors. `om-analysis` runs its jobs on `WorkerPool`. `om-midi` talks to hardware through `MidirBackend` (`midir`; port ids are `Client:Port`, without the sequencer address) or the mock backend. `om-library` and the analysis cache open SQLite with `journal_mode=WAL` and `synchronous=NORMAL`. `om-plugins` loads in-process plugins and C-ABI shared libraries, and with the `clap` feature (off by default, ADR 0007) CLAP plugins through `clack` (`clap/`, with a worker thread per instance); the CLAP first-run warning, state restore and latency readout are built, delay compensation is deferred.
- **`om-stems`**: streamed `StemSeparator` over `HtDemucsPipeline`, `StemCache`, `StemService` (one worker, explicit submit only). Details: [docs/features/stems.md](features/stems.md).
- **`om-automix`** (pure, depends on `om-core` only, control thread, never the audio thread): planner, controller, queue rules and the typed `automix` target; the app side is `automix_service`, `automix_host` and `automix_queue` in `openmixer`. Cancel rules and ids: [docs/features/automix.md](features/automix.md).
- **`om-ui`** (no window): binds ids built from `ParamId`, lists learnable targets, holds settings, preferences and the `MidiHost` trait, and the themes. The fader taper and its dB marks (`fader_law`: `FaderLaw`, `ticks`) and the knob detent pull (`control::snap_with_bypass`) live here so the GPUI and web windows share them.
- **`om-ui-gpui`** (workspace member, the default `gui` feature): GPUI drawing and events over `om-ui` models. It builds on `gpui-pre` 0.3.10 (imported as `gpui`) and `gpui-kit` 0.8.1; buttons, inputs, the library `DataTable`, sidebar rows, settings tabs, dialogs and toasts are `gpui-component` widgets themed by `theme_bridge`; knobs, faders, meters, waveforms, the platter and the sampler pads stay custom-painted. `desktop` and `media_keys` hold the file pickers, clipboard, notifications and OS media keys (`souvlaki`); `plugin_window` hosts a CLAP plugin's window.
- **`om-ui-bridge`** (no window dependency, tested headless; ADR 0009): the wire formats of the web front end. `pack_snapshot` (the 30 Hz binary snapshot packet, version 2), `pack_peaks` (waveform levels at four bytes per point, the heights the GPUI strip draws), `theme_css` (theme tokens and density metrics as `--om-*` CSS variables), `slice_control_ids` and `slice_controls` (each front-end control key with its canonical id and the range, default, detent, kind and label of its `om-ui` widget model, plus the travel law, dB marks and detent pull GPUI applies to it: `control_law`, and a knob's `Readout`; then the composite `deck<d>.cue`, whose ordered `writes` are GPUI's Cue), `caption_text` (a knob's value as GPUI prints it under the label) and `dispatch_control` (validated `ParamId` dispatch). `fixtures/ui-bridge/` holds the golden packet, the meter table, the fader law table and the knob text table both sides test.
- **`om-ui-tauri`** (workspace member, the `gui-tauri` feature of `openmixer`, off by default; ADR 0009): the Tauri v2 window, the web front end that is to replace the GPUI window at the cut-over; until then mock device only. It owns the Tauri commands and the `deck-changed` event, the snapshot stream thread (`om-ui-stream`), the control thread that builds the demo library and pumps the track loader (`om-ui-control`), per-deck lane ink (`strip_ink_dto`, from `om_ui::waveform::StripInk`), the `--ui-bench` report, the `--ui-drive-out` layout map and state file (for `tools/ui-drive.py`) and the smoke watchdog. The Svelte 5 front end is in `web/` (WebGL2 waveform lanes, DOM controls), the app icon sources and `render.sh` in `icons/`. `build.rs` writes a placeholder page when `web/dist` is not built, so the workspace compiles without Node; Linux builds need `libwebkit2gtk-4.1-dev`. Details: [docs/features/tauri-trial.md](features/tauri-trial.md).
- **`om-testing`** (dev-dependency only; no shipped crate depends on it normally): shared test support: WAV fixtures and a reader, deterministic signals, a synthetic music-like mix, gain and level measures, condition polling (`assert_eventually!`) and a temporary directory removed on drop.
- **`openmixer`** (binary, composition root): `Services` (typed optional services), `AppComposition`, `AppError`, `EngineStateReader` (a `StateReader` over a fresh snapshot), and the MIDI service that implements `MidiHost`.
