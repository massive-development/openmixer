# Rotary knobs implementation plan

Status: merged in PR #115 (polish in PR #116).

Date: 2026-10-24. Branch: feat/ui-redesign. Spec: `docs/design/research/knobs.md` (read sections 3 to 5 first).

**Goal.** Replace the rectangle "knobs" (blank in `docs/screenshots/main-dark.png`: GAIN, HI/MID/LOW, FILTER) with real rotary knobs: 270 degree arc, pointer, detent tick, bipolar centre, piecewise angle mapping, value popup, shift-fine, wheel, double-click reset, keyboard. Apply to trim, EQ, filter, FX mix/params (same `knob_view`), cue mix, phones level, master, sampler gain/pitch.

**Constraints.** No new dependencies. Do not touch `Cargo.lock` (it is already modified in the working tree; never `git add` it, never run commands that rewrite it: use `cargo test --locked`, `cargo build --locked`). Clean-room (ADR 0001): every glyph drawn by us.

**Ownership.** This plan OWNS the new file `crates/om-ui-gpui/src/knob_paint.rs` and the knob functions in `crates/om-ui-gpui/src/controls.rs` (`knob`, `knob_face`, `KnobFace`, new helpers). Other plans also edit `mixer_view.rs`, `sampler_view.rs` and the layout files (`om-ui/src/widgets/{channel,cue,master}.rs`, `sampler_strip.rs`). Do all owned work first (Tasks 1 to 7, which compile and pass without touching those files), then apply the call-site edits in Task 8 last, as small separate commits, so merges are trivial. Rebase on the other plans before Task 8.

**Current facts (verified in the repo).**
- `knob_face(t, rect, KnobFace{label,readout,detent,active}, (value,min,max), target, abs, cx)` draws a rect body plus a vertical fill; `knob_view` in `mixer_view.rs` calls it for trim, EQ, filter, FX. The deck stem filter calls the compact `knob(...)`.
- `drag.rs` `Target::is_knob()` lists Trim, Filter, Eq, FxMix, FxParam only. Knob drag is linear in value: `anchor_value + travel/200px * (max-min)`, then `Knob::snap_to_detent`. Reset is double-click in `draggable` (`click_count >= 2`), via `reset_target`/`default_of`.
- Cue mix and phones are `Ranged` (`CueSection.mix`, `.level`), master is `Ranged` (`MasterSection.fader`), drawn with `slider_with_popup`. `Target::CueMix/CueLevel/Master` exist but are not `is_knob()` and `knob_of()` returns None for them (no detent).
- Sampler gain/pitch are `-`/`+` buttons calling `sampler_step_gain(+-0.1)` / `sampler_step_pitch(+-1.0)`; model is `PadView.gain` (linear, default 1.0) and `.pitch` (semitones). Layout in `om-ui/src/widgets/sampler_strip.rs` (`gain_down/gain_value/gain_up`, `pitch_*`).
- Layout is rect based and not square: wide knobs are full strip width x 40 px (`WIDE_KNOB_HEIGHT`), EQ cells are about (strip_w/3 - 2) x 56 px (`BAND_KNOB_HEIGHT`), cue is two half-width x 32 px cells.
- Value ranges: trim 0..4 linear, unity 1 (readout Gain); EQ -48..+6 dB, 0 detent, -48 = KILL; filter -1..1, 0 detent; cue mix 0..1 default 0; phones 0..MAX_GAIN default 1.
- `waveform_paint.rs` shows how `PathBuilder` + `window.paint_path` are used; `deck_view.rs` uses `canvas`. `crates/om-ui-gpui/tests/style_lint.rs` forbids raw colour literals: all colours must come from `ThemeTokens`/`LookAndFeel` (`paint()` converts).

## Design decisions

1. Pure math lives in `knob_paint.rs` as plain functions (no gpui types in signatures), so every test below runs headless. Painting is a thin `canvas` over them.
2. Angles are degrees clockwise from 12 o'clock. `SWEEP_START = -135.0`, `SWEEP_END = 135.0`.
3. Piecewise map `angle_of(value, min, detent: Option<f64>, max)`: with a detent, `[min, detent]` maps to `[-135, 0]` and `[detent, max]` to `[0, 135]` (pointer at 12 o'clock on the detent, per spec section 3); without, linear over the full sweep. `fraction_of_angle` is its inverse. Handle degenerate detent (`detent <= min` or `>= max`) by falling back to linear.
4. Dragging operates on the **sweep fraction** (0..1 of the 270 degrees), not raw value: `frac = angle_frac(anchor_value) + dy/200px`, shift divides travel by 10, then `value_of(frac)`. This is what makes the pointer follow the mouse for EQ/trim. Keep `KNOB_TRAVEL_PX = 200`. This replaces the linear arithmetic in `drag_move` for knob targets only; faders are untouched.
5. Knobs are circles inscribed in their rect: `knob_geometry(rect, label_h) -> KnobGeom { cx, cy, r_cap, r_track }` centres the circle in the rect, diameter = min(w, h - label_h), capped at the role maximum (36 px). The hit area is the **square bounding box** of the track arc, not the rect, so a 40 px-tall, 200 px-wide GAIN bar does not turn the whole strip width into a knob. Label sits beside or below the knob inside the same rect.
6. Detent tick for bipolar; at rest a 2 px centre dot replaces the value arc. Kill zone (EQ bottom 5% of sweep, `value <= min + 0.05*(detent-min)`) draws in `danger`.
7. Theme: add `knob.track`, `knob.pointer`, `knob.kill` to `KnobStyle` in `om-ui/src/style.rs` with defaults derived from existing tokens (`border_strong`, `text_primary`, `danger`) so old theme JSON loads without warnings (derive, do not require new JSON keys). If adding fields to the JSON schema is required later, treat it as a separate task.

## Tasks (strict order, tests first, commit after each)

### Task 1. Angle mapping (pure, in `knob_paint.rs`)
Create `crates/om-ui-gpui/src/knob_paint.rs`, register `mod knob_paint;` in `lib.rs`. Write the failing tests first in `#[cfg(test)] mod tests`:
- `unipolar_ends_hit_sweep_ends`: `angle_of(0,0,None,1) == -135`, `angle_of(1,..) == 135`, midpoint 0.
- `eq_detent_sits_at_twelve_oclock`: EQ (-48, Some(0), 6): `angle_of(0.0) == 0.0`, `-48 -> -135`, `6 -> 135`, `-24 -> -67.5`, `+3 -> 67.5`. (A linear map would put 0 dB at 89% of the sweep.)
- `trim_unity_at_twelve`: (0, Some(1), 4): `1.0 -> 0`, `0 -> -135`, `4 -> 135`.
- `filter_is_symmetric`: (-1, Some(0), 1): `0.5 -> 67.5`.
- `round_trip`: for 200 sampled values on each of the three knobs, `value_of_angle(angle_of(v)) ~= v` within 1e-9.
- `out_of_range_clamps` and `degenerate_detent_falls_back_to_linear` (detent equal to min).
- `kill_zone`: `in_kill_zone(-48.0, ..)` true, `-46.0` true (within 5% of 48 = 2.4), `-40.0` false, true only for knobs with kill (flag on the call).
Then implement `angle_of`, `value_of_angle`, `SWEEP_START/END`, `in_kill_zone`. Run `cargo test --locked -p om-ui-gpui knob_paint`.

### Task 2. Fraction-based drag math
Failing tests (still in `knob_paint.rs`, function `dragged_value(anchor_value, dy_px, fine: bool, min, detent, max) -> f64`):
- `up_is_more`: dy positive (pointer up) increases value; 200 px up from `min` reaches `max`.
- `shift_is_ten_times_finer`: 20 px with shift == 2 px without.
- `eq_drag_tracks_pointer_angle`: from 0 dB, 100 px up moves the pointer exactly +67.5 degrees (i.e. the value `+3` dB), not `+27` dB.
- `clamps_at_ends`.
Implement. Then add `snap_with_bypass(knob, value, shift)`: detent pull (existing `Knob::snap_to_detent`) is skipped when shift is held. Test `shift_bypasses_detent_pull`.

### Task 3. Geometry and hit-testing (squareness)
Failing tests first:
- `geom_is_square_and_centred` for rects 200x40 (GAIN), 58x56 (EQ), 106x32 (cue), 24x24 (stem), 28x28: diameter == min(w, h - label_h) capped at 36, `cx,cy` is the rect centre, track bbox fits inside the rect.
- `hit_test_inside_circle_only`: `hits(geom, point)` true at centre and at 0.9 r, false at the rect corner and at 200x40's far-left edge (the wide bar must not be one big hit area), false in the 90 degree gap? (No: the gap is still part of the knob; hit the whole disc.)
- `small_knob_drops_ticks_and_label`: below 32 px no scale ticks; below 28 px stroke is 2 px (spec section 3); `stem` role (24 px) hides label.
- `popup_anchor_is_above_knob_top`: popup top uses `geom.cy - r_track - POPUP_LIFT`, clamped to >= 0 of the card.
Implement `KnobRole {Wide, Band, Cue, Fx, Sampler, Stem}` with max diameters 32/32/36/30/28/24, `knob_geometry`, `KnobGeom::hits`. These replace `rect`-sized hit areas: the draggable wrapper in Task 5 is sized to `geom` bbox, not `rect`.

### Task 4. Paint
Implement `paint_knob(window, bounds, KnobPaintState{ geom, angle, detent_angle: Option<f32>, bipolar, killed, hovered, active, disabled }, colours)` inside `canvas(...)`:
- Arc helper `arc_path(cx, cy, r, a0, a1, stroke)` using `PathBuilder::stroke(w)` + `arc_to`; split at 180 degrees (arc_to endpoint form). Unit-test the helper's endpoint/flag maths (`arc_segments(a0,a1) -> Vec<(a_start, a_end)>`: `-135..135` yields two segments each <= 180; `0..0` yields none; reversed args normalise).
- Track arc (full sweep) in `knob.track`; value arc from min (unipolar) or detent (bipolar) to the value in the channel accent (`kill` when killed); cap = filled circle (`paint_quad` with full corner radius) in `surface_raised` with 1 px `border_strong`; pointer = two-point stroke from 35% to 85% of cap radius, 2 px, `knob.pointer`; detent tick 2 px outside the track; bipolar-at-rest 2 px centre dot; 3 scale ticks only at diameter >= 32 px.
- Round caps unverified in gpui 0.2.2 (spec section 5): first write a 20 line prototype (a throwaway test example, not committed) painting one arc; if caps are square, cap arc ends with small filled circles.
- Cache static track/tick paths per (diameter, theme) in a small `HashMap` held in `Shell`-independent `thread_local!`; rebuild only value arc and pointer. Do this last, after measuring (spec: under 40 small paths per frame; do not optimise early).
Painting itself is verified visually (Task 9); no unit test beyond the helper maths.

### Task 5. Widget API in `controls.rs`
Failing tests (headless where possible: pure helpers returning event outcomes, `controls.rs` keeps logic in `fn` taking plain values):
- `wheel_step(value, notches, shift, min, detent, max)`: one notch = 1/100 of the sweep fraction, shift = 1/1000; direction sign test.
- `key_step(key, shift, ...)`: Up/Right +1 step, Down/Left -1, Shift fine, Home -> reset value, End -> max, PageUp/PageDown = 10 steps; unknown key returns None.
- `ctrl_click_resets`: `is_reset_click(click_count, ctrl_or_cmd)` true for double-click or ctrl/cmd-click.
Implement `knob_face` anew with the **same signature** (so `knob_view` compiles unchanged) plus `role: KnobRole` inside `KnobFace` (default `Band`) and an optional `accent: Option<Colour>`. Body: a `div` sized to `rect` with the circle `canvas` child and optional label; a draggable/hoverable/focusable (`focus_handle` via `Shell`; reuse the pad pattern in `sampler_view.rs`) hit element sized to `geom` bbox. Wire:
- `on_mouse_down`: ctrl/cmd or `click_count >= 2` -> `reset_target`; else `begin_drag` (record `ev.modifiers.shift` into `Drag.fine`).
- `on_scroll_wheel`: `wheel_step` through `Shell::apply`.
- `on_key_down` when focused: `key_step`.
- hover: unchanged (`Shell.hovered`), popup via existing `popup()` anchored per Task 3.
Keep `knob()` (the compact stem knob) as a mini bar for now: 24 px stem knobs lose legibility (spec section 5); switch it to the Stem role (no label, value on hover, no ticks) only if the Task 9 screenshot reads well.

## Risks
- **Non-square rects.** Handled by `knob_geometry` and a bbox hit element (Task 3), but a 200x40 GAIN bar leaves 160 px of dead space; label goes beside the knob there. If it looks empty, widen the label or put the readout at rest in the dead space (against the spec, so ask first). Layout row heights may need the +-4 px tweak in Task 8, which collides with other layout plans: sequence last.
- **24 px stem knob** (deck_view `knob()`): below legibility for arcs, no ticks or label. Keep it a mini slider unless the screenshot is clean; do not block the plan on it.
- **gpui `PathBuilder` quality.** Round caps and `arc_to` for 270 degrees are unverified; the Task 4 prototype decides between stroke caps and circle caps. Antialiasing at 2 px strokes may look thin; tune stroke by eye.
- **Fraction drag changes feel** versus linear drag (spec section 5): trim and EQ no longer move linearly per pixel; the tests in Task 2 and 6 lock the intended behaviour.
- **Model type change** (`Ranged` -> `Knob` for cue/master) touches `debug_panel.rs`, `drag.rs`, `mixer_view.rs`, binding code: compile errors guide it; other plans editing the same lines conflict, hence Task 7 is split from Task 8.
- **Sampler per-pad state** and empty pads: knob must be disabled, not panic, when no pad is selected or loaded.
- **Keyboard focus** needs `FocusHandle`s per knob in `Shell`; follow the sampler pad pattern, create them lazily keyed by `Target`.
- **Soft takeover / MIDI mismatch ring**: out of scope.
- **Theme keys**: derived defaults avoid new JSON keys (decision 7); if a theme file omits them nothing breaks.
